# 记录与恢复

## 轻量交接

单人单任务、短项目，或用户只要一份交接时，先沿用已有交接或当前状态文档。没有时，在已有文档目录新建交接，按用户或项目语言命名，如中文 `交接.md`、英文 `HANDOFF.md`；没有合适目录就放在根目录，仅当现有布局需要时另建文档目录。保持一份主要状态来源，不为统一命名另建文件。

正文按需要写目标与边界、当前进展、关键决定及原因、验证结果、未完成或阻塞、下一步，并链接相关文件或证据。不强制标题和空栏目；阶段完成或交接前更新即可。已有信息不足时先核对文件，仅补问影响继续工作的缺口。

这一路线只需宿主能读写本地文件，不需要 Python、硬链接、`scope`、日志事件或 `check`。不创建 `.ai-memory`、AGENTS、DEV 或整套骨架，不伪造事件头、项目身份、确认答复或校验值。用户或项目明确要求每任务先问时仍须遵守，当前指令只授权当前任务。

需要多个任务、可追溯的增量历史、审计或文档依赖复核时再采用下面的结构化流程，保留并链接既有交接，不把旧正文冒充脚本日志。已有结构化项目继续原体系，不自动降级或删除历史。

## 结构化任务范围

按[范围流程](interview.md)确认已有实际授权依据，保存真实指令及 AI 采用的默认项，不为内部档位重复问答。只在确需完整新项目骨架时运行 `init` 并填写真实需求；已有项目按[职责映射](adoption.md)补缺。标准/详细任务没有现成计划时运行 `task`，补齐目标、阶段和验收。精简任务可不建计划。

由 AI 准备 scope JSON。以下为结构示例，授权摘要必须改成实际指令；`plan` 若填写，必须指向已存在的项目相对路径：

```json
{
  "goal": "修复登录状态恢复并验证回归",
  "detail": "standard",
  "modules": ["android-client", "auth-service"],
  "record_fields": ["changed", "pitfall", "fix", "verification", "next", "long_term_candidates"],
  "plan": "docs/tasks/login-restore/plan.md",
  "confirmation_summary": "用户要求记录这次登录恢复修复并在之后继续；AI 根据影响面采用 standard，覆盖现有客户端和鉴权接口，沿用已有计划。"
}
```

```text
python "<技能目录>/scripts/ai_memory.py" scope --root "<项目>" --task "login-restore" --file "scope-input.json" --confirmed
```

首次配置生成项目身份；相同内容重复调用保留原记录。改变范围须有覆盖变化的实际指令或补充授权，并传入当前 `revision`，如 `--expected-revision 1`；用户已经说明的变化无需再次确认。版本已变化则读回新范围后协调，不覆盖他人的更新。旧范围保留历史，不合并不同任务的授权。

同一任务的目标、模块、记录要求和边界没有实质变化时，沿用原范围；换会话或重新表述同一授权，不需要新增范围版本。当前进展和验证写入本轮记录。

新范围文件最多 32 KiB，超限在写入前拒绝。详细需求与背景放入有链接的 Markdown；旧项目超大范围保留原文并提示按路径阅读。项目预设只减少问答，不自动授权新任务，见[工作流](workflow.md)。

## 保存迭代

以下仅为结构示例，字段须替换为实际观察：

```json
{
  "event_id": "login-restore-round-01",
  "actor": "codex-session-a",
  "modules": ["android-client"],
  "changed": "修正登录状态恢复的初始化顺序。",
  "pitfall": "页面先读取状态，存储尚未完成加载；增加重试没有解决根因。",
  "fix": "等待存储恢复完成后再决定页面状态。",
  "verification": {
    "status": "partial",
    "summary": "本地单元检查通过，真机进程重建尚未验证。",
    "command": "实际执行的验证命令或方法",
    "result": "真实结果或输出摘要",
    "revision": "可选：执行时的代码版本",
    "evidence": ["docs/tasks/login-restore/progress.md"]
  },
  "next": "在真机模拟进程回收后重新进入，验证登录恢复。",
  "long_term_candidates": ["状态路由等待持久化恢复；待确认。"]
}
```

精简记录可只含 `changed`、`verification`、`next`。验证支持准确文字或上述对象，状态为 `passed / failed / partial / not_run`。

```text
python "<技能目录>/scripts/ai_memory.py" record --root "<项目>" --task "login-restore" --file "event-input.json"
```

- 正式记录位于 `docs/memory/journal/YYYY-MM-DD/<event_id>.md`，目录日期使用 UTC；JSON 只是输入。
- 相同 ID 和内容重复写入幂等；同 ID 不同内容拒绝覆盖。不同代理使用不同 `actor` 和事件 ID。
- 新记录使用 v2 元数据保存 `scope_revision`；旧 v1 事件继续可读，已有项目继续写 v2，无需迁移原文。
- 错误事实在新事件中使用 `"corrects": ["旧事件ID"]`，取代旧结论用 `"supersedes": ["旧事件ID"]`。目标必须存在且不成环，不改旧事件；恢复同时显示关系，不能把旧结论继续当作当前事实。
- 交接检查只有读全并校验同任务的替代证据、且替代日志具有明确验证状态时，才把旧验证声明移入历史显示；不按时间猜测替代，也不把 `corrects` 当作整条结论失效。具体边界见[工作流](workflow.md)。
- Windows Git 的 LF / CRLF 往返可验证；只兼容换行差异，不忽略正文变化。事件哈希证明内容完整性，不证明记录者说的业务结果真实。
- 只保存必要事实，不记录密码、令牌或聊天全文。

## 检查点

阶段完成、重要设计决定、根因确认、方向变化和交接时及时记录；已知即将压缩时先保存未落盘事实。

交接至少能回答：目标和范围、停在何处、关键原因、修改范围、已验证/未验证、阻塞和下一步。未执行的验证明确写未执行，不能把计划或工具调用成功写成功能通过。

结构化项目用 DEV 或现有状态入口保留项目摘要与活动计划链接；计划维护当前阶段，日志保存增量证据。已有发现/进展文档时链接对应证据，不反复复制全文。轻量项目更新原交接文档即可。

## 状态查看与结构化恢复

只想查看项目记录状况时可运行 `status --root "<项目>"`，默认中文摘要，`--json` 输出机器可读结果。此命令只读，不为轻量或未登记项目创建配置；轻量交接仍直接阅读原文，不要求运行脚本。

```text
python "<技能目录>/scripts/ai_memory.py" resume --root "<项目>" --task "login-restore" --limit 5 --max-bytes 16384
python "<技能目录>/scripts/ai_memory.py" resume --root "<项目>" --module "android-client" --limit 5
python "<技能目录>/scripts/ai_memory.py" audit --root "<项目>"
python "<技能目录>/scripts/ai_memory.py" handoff --root "<项目>" --task "login-restore"
```

结合已有规则、状态入口、活动计划及真实工作区恢复；先报告目标、关键约束、实际完成、未验证、阻塞和下一步。相同任务的有效范围直接沿用；缺少范围文件时先核对当前指令能否建立真实依据，只有授权边界仍不明才问，不猜测未保存的信息。

`--max-bytes` 继续限制 Markdown 正文总字节；`--max-output-bytes` 限制整个 JSON 输出（默认 32768，最少 1024），包括元数据与错误，不裁剪磁盘原文。长记录优先保留验证与下一步，并标明省略；`read_required=true` 或 `required_reads` 指出关键内容缺失，先补读再恢复。总预算太小时省略数量、错误数量与补读提示仍显式报告，不能把空列表当作无问题。

范围发现独立于日志发现，刚确认但还没有日志的任务仍可找到。扫描是否完整、范围和日志省略数分别报告；多活动任务时明确选任务或建立会话绑定，不能从“最近有日志”猜当前任务。`resume` 扫描元数据并校验选中正文，历史正文完整性使用流式 `audit`。默认省略逻辑归档事件，`--include-archived` 可追溯；归档中的更正关系仍生效。

恢复按目录复用边界检查，仍逐条读取真实日志首行，构建本次调用的内存索引；不保存磁盘缓存，也不把文件时间戳当作内容未变的证明。文件或目录在扫描期间发生可检测的替换、增删时会报告扫描不完整，应等写入结束后重试。此优化不代替完整审计，也不提供对恶意本地写入者的隔离。

单独使用 `--module` 时跨任务查询该模块历史，包含暂停和已完成任务，不按唯一活动任务缩小范围。同时指定 `--task` 时以该任务为准；同时提供 `--client` 和 `--session` 时先按会话选择任务，再按模块筛选。会话参数须成对提供。确定任务后，返回的范围与日志均属于该任务，不让其他任务的范围占用 `--limit`。

## 多模块、多 AI

日志字段和模块不得超出 scope。模块名是记录分类，不是访问权限；跨模块长期规则需明确适用范围并确认。

分配任务与记录责任，日志分别写；计划、DEV 和规则由一名负责者汇总。脚本锁和 scope revision 防止脚本相互覆盖，普通编辑器不受锁保护。残留锁先核实写入者，不自动破锁。

所有当前写命令共用 `.ai-memory/store.lock` 的操作系统锁，文件存在本身不代表被占用；进程退出释放锁。发现旧版 `admin.lock` 则拒绝写入并提示核实。跨克隆不共享锁：合并后运行 `audit`，人工解决范围版本、归档清单和当前计划冲突，禁止把不同项目身份合并成一个项目。

文档和日志沿用项目版本控制与备份策略；启用记忆本身不授权提交、推送或上传。

## 无脚本能力时

轻量交接照常读写，不依赖脚本。结构化项目暂时无法运行脚本时，可直接阅读 Markdown 并沿用已有授权，在现有 progress 或普通交接文件中记录事实，从已有状态入口/索引链接并标记“人工记录，未纳入记忆库校验”。不手造项目身份、确认记录或校验值；恢复命令不会收集这些人工记录，必须沿入口阅读，后续核实后再导入。
